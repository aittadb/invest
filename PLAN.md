# Investor App Implementation Plan

This file is the flat queue of accepted, unfinished implementation work. Stable `TASK-NNN` identifiers must not be renumbered or reused.

Each task should be the smallest coherent increment that can finish in one focused commit with an objective pass/fail definition of done. Do not combine independent routes, storage contracts, security controls, UI flows, migrations, or live proof matrices. Completed tasks move to `CHANGELOG.md` with evidence and are removed from this file.

- [ ] TASK-005: Define campaign and phase configuration contracts. DoD: campaign identity, publication state, phase status, country eligibility, amount-rule, aggregate-display, and setup-completion contracts are typed and documented; tests cover unpublished/public visibility, restricted-country eligibility, amount minimum/increment validation, and no campaign-specific defaults.
- [ ] TASK-006: Define package content and acknowledgment contracts. DoD: package section, ordering, immutable version, content hash, material-change, acknowledgment text, and acceptance-record contracts are typed and documented; tests cover empty-section hiding, immutable snapshot creation, renewed-acceptance requirements, and unsafe Markdown rejection at the contract boundary.
- [ ] TASK-007: Define participant profile and consent contracts. DoD: access-registration profile, declared interest, account email label, marketing consent, account-deletion request state, and editable-field rules are typed and documented; tests cover first-registration requirements, profile updates, consent withdrawal, and deletion-withdraws-active-interest intent.
- [ ] TASK-008: Define investment indication contracts. DoD: personal indication, company indication, lifecycle state, company identifier normalization, acknowledgment requirement, participant-visible transitions, owner rejection, and history-entry contracts are typed and documented; tests cover one personal active indication, company duplicate non-disclosure, withdrawal/reactivation, and material-acknowledgment blocking.
- [ ] TASK-009: Define founder application contracts. DoD: founder application fields, contribution-area choices, lifecycle state, separate-from-investment rule, and history-entry contracts are typed and documented; tests cover create/edit/withdraw behavior and the ability to have founder and investor records independently.
- [ ] TASK-010: Define aggregate and reconciliation contracts. DoD: aggregate summary, contributing-state rules, stored-versus-calculated reconciliation preview, correction confirmation, and public sanitization contracts are typed and documented; tests cover active-only contribution, rejected/withdrawn exclusion, oversubscription display data, and no identity/note exposure.
- [ ] TASK-011: Define audit and manual-notification contracts. DoD: audit event shape, actor attribution policy, notification-template, copied-versus-sent distinction, export event, and redaction rules are typed and documented; tests cover audit append intent, manual sent-marker behavior, and no credential or private-note fields in public errors.
- [ ] TASK-012: Define the `StorageAdapter` contract suite. DoD: adapter interface, transaction/idempotency expectations, pagination boundary, compare-and-set requirement, non-disclosing failure shape, and shared contract-test harness are documented and typed; tests run against a minimal fake adapter proving the harness detects authorization, duplicate, drift, and disclosure failures.
- [ ] TASK-013: Implement the in-memory campaign repository. DoD: deterministic in-memory campaign/setup/phase repository passes the campaign contract tests, rejects campaign-specific defaults, preserves setup history, and documents that it is not production storage.
- [ ] TASK-014: Implement the in-memory content and acknowledgment repositories. DoD: deterministic in-memory package-version and acknowledgment repositories pass content contract tests, preserve immutable snapshots, enforce material-version acceptance requirements, and expose no private package data to unauthenticated reads.
- [ ] TASK-015: Implement the in-memory participant repository. DoD: deterministic in-memory participant/profile/consent repository passes participant contract tests, supports registration/update/deletion intent, withdraws active-interest projections through repository coordination hooks, and uses non-disclosing foreign-record failures.
- [ ] TASK-016: Implement the in-memory indication repository. DoD: deterministic in-memory personal/company indication repository passes indication contract tests, enforces one personal active indication, enforces company uniqueness without disclosure, records immutable history, and exposes idempotent withdrawal/reactivation/rejection transitions.
- [ ] TASK-017: Implement the in-memory aggregate repository. DoD: deterministic in-memory aggregate/reconciliation repository passes aggregate contract tests, updates totals from indication projections without double-counting retries, previews mismatches before correction, and returns only sanitized public aggregate fields.
- [ ] TASK-018: Implement the in-memory founder application repository. DoD: deterministic in-memory founder application repository passes founder contract tests, keeps founder records separate from investment indications, records immutable history, and supports edit and withdrawal by owner subject only.
- [ ] TASK-019: Implement the in-memory audit and notification repositories. DoD: deterministic in-memory audit/manual-notification repositories pass audit and notification contract tests, distinguish copied templates from sent markers, record export/reconciliation/moderation events, and redact sensitive fields from serializable evidence.
- [ ] TASK-022: Add same-URI hypermedia JSON for the public campaign resource. DoD: `GET /` negotiates HTML, `application/json`, and `application/vnd.aittadb-invest+json; version=0.1` without inspecting `User-Agent`; JSON exposes public campaign `data`, semantic `links`, and only currently available `actions`; unsupported explicit versions return `406`, responses vary on `Accept`, HTML and JSON share public campaign state, and focused tests prove representation parity.
- [ ] TASK-023: Add the authenticated participant home state. DoD: a valid configured identity session extends the public campaign resource with private-package and participant-home links and currently allowed actions; signed-out and foreign-subject requests disclose nothing private; HTML and hypermedia JSON expose equivalent capabilities from the same authorization service.
- [ ] TASK-024: Add the participant investment-interest flow. DoD: authenticated participants can create, view, edit, withdraw, and reactivate their permitted personal or company indications through equivalent HTML forms and hypermedia actions; authorization, acknowledgment, validation, history, and non-disclosing duplicate behavior are tested.
- [ ] TASK-025: Add the participant founder-interest flow. DoD: authenticated participants can create, view, edit, and withdraw a founder application independently from investment indications through equivalent HTML forms and hypermedia actions; ownership, validation, history, and separation behavior are tested.
- [ ] TASK-026: Add the owner campaign workspace. DoD: authorized owners receive setup, package, participant, indication, founder-application, reconciliation, export, audit, and manual-notification navigation based only on currently allowed actions; non-owners receive no owner links or state; every owner HTML control has an equivalent hypermedia action and focused authorization tests.
